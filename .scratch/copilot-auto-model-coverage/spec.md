# Copilot Auto 模型覆盖与会话迁移

Status: ready-for-human

## Problem Statement

使用者希望在保持请求模型 ID 不变的前提下，尽可能多地利用 GitHub Copilot Auto session。现有实现从 `/models/session` 获取候选模型和一份会话令牌；在已观测的 business 账户上，这个端点只返回一个候选模型。新的 `/auto` 会根据档位和探测题目返回选中的模型 ID、该模型专用的 session token 和到期时间。服务需要在启动时发现更多模型与 token 配对，并在请求模型命中配对时使用对应 token。未命中的请求保持现有行为。

本次观测只覆盖有限请求和 business 账户。难题重新取样一次仍可能选中与简单题相同的模型；规格要求报告取得的模型 ID，不保证选出某个指定模型，也不根据有限观测推断 Auto 的完整候选集合。

## Solution

服务启动时向 `/auto` 发送四个档位各两种题目：简单题为 `hello`，难题包含从当前仓库运行时代码中随机选取的连续 100 行，并要求指出最可能的正确性问题及确认所需的信息。每次成功响应按实际 `selected_model.id` 保存会话令牌及到期时间。同档难题与简单题返回同一模型时，重新取样并再探测一次；随后接受上游结果。重复模型只保留一份有效配对。档位和题目仅用于启动探测，传入请求只按最终上游模型 ID 查找配对。

服务在启动阶段发起全部探测；失败的探测点保持待重试状态，不妨碍其他点继续执行。服务开始接收请求后继续补采，已取得的配对立即可用。过期或因 Copilot 凭据变化而失效的配对重新取得。命中的请求使用对应 session token；未命中或缺少适用端点的请求继续正常发送。Auto 查表与是否开启 `-F` 无关。计费继续使用上游返回的成本数据，不重复计算折扣。

## User Stories

1. 作为 API 使用者，我希望请求的模型 ID 保持不变，以便得到我明确选择的模型。
2. 作为 API 使用者，我希望已发现模型的请求自动使用其 Auto session token，以便获得该路径提供的计费结果。
3. 作为 API 使用者，我希望未发现模型的请求继续正常执行，以便探测覆盖率不影响可用性。
4. 作为 API 使用者，我希望开启 `-F` 时可以使用 Auto 配对，以便保留现有请求意图处理并扩大 Auto 命中。
5. 作为 API 使用者，我希望关闭 `-F` 时仍可以使用 Auto 配对，以便 Auto 不受该启动标志限制。
6. 作为 API 使用者，我希望请求只在模型与会话令牌对应时附带 token，以便避免跨模型令牌导致的上游错误。
7. 作为 API 使用者，我希望请求采用该模型支持的上游端点，以便避免把有效配对用于不支持的请求方式。
8. 作为 API 使用者，我希望普通请求遇到 400 或 401 时保持原有错误处理，以便避免因 Auto 逻辑重发无关请求。
9. 作为 API 使用者，我希望附带 Auto token 的 HTTP 推理在遇到 400 或 401 时至多重试一次，以便处理失效配对并防止无限重发。
10. 作为 API 使用者，我希望重试仍使用原请求模型 ID，以便没有任何隐含的模型替换。
11. 作为 API 使用者，我希望第二次推理请求仍失败时收到原有错误，以便准确识别上游失败。
12. 作为运维人员，我希望启动时探测 `efficiency`、`balance`、`intelligence` 和 `fast`，以便扩大可发现模型范围。
13. 作为运维人员，我希望每个档位同时使用简单题和难题探测，以便提高取得不同模型的机会。
14. 作为运维人员，我希望难题来自本次运行所在仓库的连续 100 行真实代码，以便保持探测内容与本项目相关。
15. 作为运维人员，我希望同档难题没有取得新模型时重新抽样一次，以便增加发现其他模型的机会。
16. 作为运维人员，我希望重新抽样后按实际返回结果更新配对，以便不会把“难题必得更强模型”写成未经验证的保证。
17. 作为运维人员，我希望八个探测点互不阻断，以便某一请求失败后仍能尝试其他档位和题目。
18. 作为运维人员，我希望临时失败的探测点在服务启动后继续补采，以便覆盖率能够随着上游恢复而增加。
19. 作为运维人员，我希望服务启动等待时间有上限，以便上游持续故障时仍可处理正常请求。
20. 作为运维人员，我希望同一探测点始终只有一个在途请求，以便避免重复请求扩大上游压力。
21. 作为运维人员，我希望 429 响应遵守 `Retry-After`，网络失败及上游 5xx 采用有间隔的重试，以便避免持续高频探测。
22. 作为运维人员，我希望 `/auto` 鉴权失败时暂停该实例的相同探测，待凭据变化后继续，以便避免无效的重复鉴权请求。
23. 作为运维人员，我希望持续的请求格式错误被明确报告，以便排查请求头或请求体，同时保留尚未完成的探测点。
24. 作为运维人员，我希望启动日志只列出实际取得的不同模型 ID，以便直接看见当前 Auto 覆盖范围。
25. 作为运维人员，我希望日志不出现 session token、Copilot token 和抽样代码，以便保护凭据与代码内容。
26. 作为维护者，我希望每条配对按上游的到期时间更新，以便不会发送已过期令牌。
27. 作为维护者，我希望 Copilot token 变化时旧配对立即失效并重新补采，以便避免沿用不属于当前凭据的会话。
28. 作为维护者，我希望重新探测返回不同模型时按新模型 ID 登记配对，以便映射始终与上游选模结果一致。
29. 作为维护者，我希望多个请求同时需要刷新时共享在途工作，以便不会重复创建大量会话。
30. 作为维护者，我希望保留上游折后 `cost_per_batch` 的现行成本计算，以便避免重复应用 10% 折扣。

## Implementation Decisions

- 保留“传入模型命中 Auto 覆盖范围时才附加会话令牌”的现有行为。Auto 不覆盖客户端指定的模型 ID。
- 用 `/auto` 的 `selected_model.id` 与 `session_token` 取代旧 `/models/session` 的候选集合。旧端点不再承担 Auto 配对构建职责。
- 启动探测的组合为四档乘两种题目。简单题使用 `hello`；难题使用当前源码树内可读取、足够 100 行的 TypeScript 文件，随机选取文件与连续起点。没有符合要求的源码时报告探测未完成，正常请求路径保持可用。
- 难题与同档简单题得到同一模型 ID 时仅重新取样一次。重试后的结果如实登记，不以模型名称或价格字段推断质量等级。
- 同档简单题失败时仍执行难题；只有两次探测均返回模型 ID 时才比较结果。难题获得不同模型仅表示覆盖增加，不作为模型质量保证。
- 每个成功响应按真实模型 ID 建立配对。每条配对记录 token、上游 `expires_at`、支持的端点，以及取得配对时的 Copilot 凭据标识。同一模型存在多个有效 token 时保留一条即可。
- 档位与探测题目不参与运行时匹配；运行时按实际将要发送的上游模型 ID 查找有效配对。与 `-F` 开关无关。
- HTTP 推理使用模型支持的端点；该配对不适用于请求端点时不附加 token。本机磁盘配置关闭 Responses WebSocket，本规格按 HTTP 场景验收。
- `/auto` 请求使用现有 Copilot 模型请求身份信息，明确设置 JSON `content-type`，并使用当前代码提供的 API 版本。选模响应至少校验模型 ID、session token 和可用到期时间；无效响应不进入配对表。
- 以每条响应的 `expires_at` 为准，在到期前五分钟安排刷新。重新选中的模型发生变化时，按新模型 ID 更新映射，不把新 token 写到原模型名下。
- Copilot 凭据变化时使旧配对失效。建图与请求并行时，旧凭据下发起的探测结果不能加入新凭据的映射。刷新请求共享在途任务，避免同一探测点并发重复执行。
- 启动时触发全部探测点并限制等待时间；成功的配对立即可用。未成功的探测点保留状态，服务启动后继续尝试。任一探测点失败不得阻断其他探测点。
- 网络失败与上游 5xx 按 1 秒起步、30 秒封顶的随机退避间隔重试。429 优先使用 `Retry-After`。`/auto` 返回 401/403 时暂停该实例相同凭据下的盲目重试，凭据变化后恢复。持续的请求格式类 400 记录为待处理问题，不反复发送相同请求；其他探测点继续执行。
- HTTP 推理收到 400/401 时，只有本次附带了 Auto token 才使对应配对失效并重试一次。不根据错误正文匹配；未附 token 的请求不触发 Auto 重试。系统实际调用 `/auto` 重新取得且重取失败时，将刷新错误传出并停止本次请求，不发第二次推理；旧 401 迟到、配对已被并发清除且无需重取时，仍为原模型无 token 重试一次；其余第二次失败按原有错误路径返回。
- 启动成功日志只输出当前取得的不同模型 ID；失败报告只包含可用于排查的状态与未完成数量。不得输出任何 token、请求中的源代码、档位或题目类型。
- 计费继续使用上游返回的 nano 单位成本数据；`discounted_costs` 不再次参与计算。

## Testing Decisions

- 主要测试入口为现有的完整 Copilot 请求路径：验证最终上游模型 ID、HTTP 端点、`Copilot-Session-Token` 请求头、响应状态与现行错误透传。启动预热与认证更新作为另一处可观察入口；缓存本身只对独立的时间及映射规则做必要验证。
- 延续现有 Auto 调用链、启动预热、日志、Copilot HTTP 发送及 token 元数据更新测试所保护的行为。迁移时清除旧端点断言；无法反映新行为的旧测试应改写或删除。本地单元/集成测试可以使用有明确验证目标的替身（fetch mock 或 Bun.serve）隔离外部服务，验证 `/auto` 请求形状、会话配对、端点适用与错误路径；不得加入只为让测试通过的替身，不得把本地通过结果冒充真实账户验收；真实 business 账户验证按下一条单独授权执行。
- 获得明确授权后，使用真实 business 账户验证四档简单题与难题、同模型推理成功、不同模型令牌的错误、折扣成本字段以及 token 到期信息。上游请求可能产生费用；无凭据的常规检查只验证确定性的映射和状态处理。真实探测记录请求条件与观测时间，不把选中的具体模型名写成永久断言。
- 分别验证开启与关闭 `-F` 时的模型命中与未命中路径。当前运行的五个实例全部开启 `-F`，关闭情形尚需单独验证。
- 验证每个探测点都得到尝试；单项失败时其余点继续；成功后可按模型 ID 命中；临时失败恢复后后台补采生效；启动等待不会无限延长。
- 验证同一模型被多个档位选中时查表正常、难题重采一次后仍可同模型、每条过期时间独立生效、Copilot 凭据变化清空旧配对，以及过期刷新选择新模型时不会出现 token 与模型错配。
- 验证 429 的 `Retry-After`、网络或 5xx 的退避，以及 `/auto` 的 401/403 暂停与请求格式类 400 的报告。HTTP 推理仅在附带 Auto token 且收到 400/401 时重试一次；其他失败保持原有行为。
- 验证启动日志展示去重后的模型 ID，同时不存在 token、源代码、档位和题目类型。验证成本计算沿用上游提供的折后成本。

## Out of Scope

- 替客户端改变模型 ID，或者按传入请求的内容判断难易并重新选模。
- 保证某档位一定返回更强模型、保证找到特定 GPT 型号，或者凭模型目录的折扣字段推断完整候选池。
- 本次源码运行场景之外的 Docker 镜像、发布包源码资源准备。
- WebSocket Auto session 支持；当前本机配置关闭 Responses WebSocket。
- 调整现有 `-F` 配额与请求意图逻辑、改动上游成本计算，以及跨进程共享配对表。

## Further Notes

- 2026-10-07 对一个 business 实例的探测中，旧 `/models/session` 只返回一个模型；新 `/auto` 返回被选模型、对应会话、到期时间和折扣信息。跨模型使用会话的请求曾返回 400；新 token 有效期曾观测为 24 小时。运行时始终使用每次响应携带的到期时间。
- 当前仓库已有规范仍描述旧 `/models/session` 行为。实施迁移时应同步更新该规范，避免保留两种互相冲突的运行时说明。
