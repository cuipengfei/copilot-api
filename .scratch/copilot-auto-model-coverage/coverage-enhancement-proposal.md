# Auto 模型覆盖增强提案

## Idea

提高配置目标模型获得可用 Auto 配对的机会，并让请求首次 miss、配对临近过期和令牌被拒绝时使用同一套按目标模型补采行为。

当前本机配置已将 `gpt-6-sol` 更新为 `gpt-6.1-sol`，并通过应用配置加载与目标列表解析验证。当前覆盖清单为 `gpt-6-luna`、`gpt-6.1-sol`、`gpt-6-astra`。固定题目集中迁移已完成（`src/lib/auto-probe-prompts.ts`，启动预热、定向补采与刷新共用）；retry on miss 有界共享补采已实现（冷/过期 miss 共享单飞定向轮，前台最多等 2 秒，一轮耗尽冷却 10 分钟）；五个新输入条件等其余增强仍为提案未实施。现有运行进程未由本次操作触发重新加载或重启。

建议覆盖清单再纳入已实际选到的 `mai-code-1.1-flash`；这项属于提案，本次配置修改仅替换 Sol 的名称。

## Requirements

### 已验证依据

- 正式实验包含两个不同账户、524 个有效选模样本。两个账户均选到四种模型。
- `efficiency` 的 75 个样本全部选到 GPT-6 Luna。
- Mai Code 1.1 Flash 的全部 6 次命中均来自极短回复任务与 `fast`；首验证窗口命中 4/10，第二窗口为 1/10。
- 系统性代码分析与 `intelligence` 在首窗口的 Astra 命中为 account1 12/20、account2 13/20；普通程序说明与同一档位为 9/20、7/20。第二窗口四组全部为 0/20。
- 同一请求正文、同一客户端 SessionId、同一完整评分向量可以选到 Sol 或 Astra。条件有效性具有时间变化，单次未选中不能判定目标不支持 Auto。
- 本轮仅验证 Sol 与 Luna 的实际文本生成。Astra 与 Flash 的实际生成尚未验证。

### 现有行为与需增强的位置

- [auto-session.ts](mdc:src/lib/auto-session.ts) 已有模型到令牌的配对缓存、凭据绑定、过期检查、刷新计时器、启动探测、共享定向发现与在途合并。
- 现有定向发现最多执行四档各十次，交替使用问候和 URL 规范化代码任务；常规间隔三秒。
- 配置目标没有可用配对（冷 miss 或配对过期）时，请求触发共享定向补采：单飞轮在途则直接加入等待，前台最多等 2 秒；等待超时、未配置或冷却期内按既有无令牌方式继续。清单外模型零探测。
- [auto-session-retry.ts](mdc:src/services/copilot/auto-session-retry.ts) 的令牌拒绝处理调用固定问候与 `balance` 的刷新，之后查询原模型配对；该刷新不保证得到原模型。

### 验收要求

1. Given 请求模型属于覆盖清单且没有可用配对，When 请求发生 miss，Then 触发一次按目标补采；同一实例和凭据下的并发请求共享探测任务。
2. Given 当前端点不能使用已有有效配对，When 请求查询令牌，Then 按现有无 Auto 令牌行为处理，不因端点不兼容反复探测。
3. Given 上游此次选到另一模型，When 保存响应，Then 只按实际选中模型登记配对；请求仍使用原模型，不能把另一模型的令牌绑定给原模型。
4. Given 某模型配对临近过期，When 刷新未选到该模型，Then 保留其尚有效的旧配对，继续按预算补采；刷新完成不能仅以旧配对仍有效判定。
5. Given 原配对被上游判定失效，When 尝试恢复，Then 使用按目标补采并保留一次业务请求重试上限；已移除的无效令牌不得再次附着。
6. Given 任意补采任务，When 凭据轮换或服务停止，Then 旧凭据的迟到响应不得登记；沿用现有 401/403 暂停和 429 退避。
7. Given 一个条件本轮未选到目标，When 规划后续探测，Then 尝试其他候选条件并执行冷却；不能据此把模型永久标为不可用。

## Tasks

- 将启动发现与定向发现的输入策略集中为同一套有实验依据的条件集合。
- 改造现有定向发现调度，统一处理无配对、临近过期和令牌拒绝；继续复用现有缓存和凭据检查。
- 让普通配置目标 miss 可加入共享补采任务，并设置前台等待上限。
- 让令牌拒绝后的恢复按原模型获取配对，迁移相关调用并移除不再使用的固定问候刷新路径。
- 为现有成功来源记录增加条件识别与成功时间；选择近期实际命中过目标的条件，并在条件失效后更换。
- 更新受影响的行为测试和既有覆盖说明，再执行仓库要求的全量检查及独立进程真实后端验证。

## Design

### 条件集合

| 输入任务 | 档位 | 本次观察支持的用途 |
|---|---|---|
| 明确要求极短回复，例如只回复 hi | efficiency | 获取 GPT-6 Luna 的配对 |
| 同一极短回复任务 | fast | 增加选到 Mai Code 1.1 Flash 的机会，也能获得 GPT-6 Luna |
| 说明完整程序的行为、输入、输出、状态变化 | intelligence | 获取 GPT-6.1 Sol，部分时段也能选到 GPT-6 Astra |
| 具体修改程序功能或检查并发、取消问题 | balance | 增加代码任务的选择变化，常选到 GPT-6.1 Sol |
| 完整代码正确性分析，包括状态模型、调用关系、异常与并发不变量 | intelligence | 增加在可命中时段选到 GPT-6 Astra 的机会 |

代码条件使用一份长度受控的完整源码材料；同轮不同任务复用该材料，减少随机片段差异。该材料属于现有源码采样范围，不追加发送真实用户请求内容。

探测实现不包含固定的模型名称到档位映射。条件集合固定，实际模型到成功条件的关系由本实例真实响应建立。模型 ID 按完整字符串匹配，型号变化由覆盖配置处理。

### 题目定义与保存（已确认）

现有三个固定文本（hello、URL 规范化任务、正确性问题题干）已迁移到独立的 `src/lib/auto-probe-prompts.ts`，由启动预热、定向补采和到期刷新共用；该模块只导出这三个文本，条件 ID、档位与材料需求仍属于下方待引入模板，未实施。

本节五个条件来自本轮实验，属于待引入的模板，尚未实施。retry on miss 有界共享补采已实现（`src/lib/auto-session.ts`：`TARGET_MISS_WAIT_MS` 前台等待、单飞定向轮共享、耗尽 10 分钟冷却、等待者凭据快照与轮换唤醒），不属于本题字迁移。

近期成功来源继续保存在现有进程内存记录中，不新增持久化题库。模型覆盖清单继续保存在用户配置。题目保持固定措辞，同轮代码题共享材料，便于比较实际选模结果。

### 按目标补采

保留 [getAutoSessionTokenForModel](mdc:src/lib/auto-session.ts) 的现有调用方式，将补采行为集中到现有 Auto 会话管理中（已实现：共享单飞定向轮，一次选择更新多个请求随后需要的缓存，不为每个目标独立重复同一探测）。按"近期成功条件优先、其余条件探索"的规划属于下方待引入的五条件模板，未实施；已实现的 miss 路径使用既有固定题目。

前台 miss 最多等待一次补采，等待上限两秒（已实现，超时仅结束该请求等待，不取消共享探测；当前请求按现有无 Auto 令牌方式发送原模型，迟到的合法结果可供后续请求使用）。

后台补采沿用现有定向发现轮（四档 × 十次、单飞、三秒间隔）服务全部缺失目标；本节原建议的"每轮最多五次 /auto"上限未实施。全部目标覆盖后停止缺失补采；临近过期刷新使用单独的完成条件。

本轮耗尽仍缺失时进入十分钟冷却（已实现），冷却结束重新检查仍缺失目标后再进行有界探测。两秒和十分钟是建议的工程限制，未验证为最优值。沿用现有启动等待上限，补采不阻止服务启动。

### 配对安全与刷新

只使用实际选中模型的完整 ID、同一次响应中的令牌、有效期、支持端点和当前凭据登记配对。缓存继续限定在同实例和凭据，不共享跨实例令牌。

临近过期刷新失败不删除旧有效配对；实际过期或被拒绝的配对不能用于请求。保留既有并发失效检查，迟到拒绝不能删除其他请求已经更新的配对。

当前窗口未取得目标时保留未覆盖状态，后续窗口仍可尝试。覆盖状态表示持有可用配对，不表示已经验证该模型的生成质量或能力。

## Test Cases

- 配置中的目标首次 miss 可以触发补采；清单外模型和端点不兼容不会额外触发探测。
- 并发 miss 共享任务；前台等待超时不会取消其他等待者使用的探测。
- 未选到目标但选到另一模型时，实际模型获得缓存，原模型不获得错误配对。
- 临近过期的旧配对在未命中刷新时仍可用；过期后不能附着旧令牌。
- 令牌拒绝仅触发一次业务重试；并发取得的新配对不会被迟到错误删除。
- 凭据轮换、429、401/403、停止与冷却期间的 miss 保持已有收敛和退避规则。
- 真实已保存选模结果用于检查条件选择与统计；实际令牌取得、配对和生成使用独立进程及真实上游验证，不使用 mock。
- 真实验证按账户、时间窗口、条件分别报告覆盖模型、请求次数和等待时间；选模与实际生成分别记录。
